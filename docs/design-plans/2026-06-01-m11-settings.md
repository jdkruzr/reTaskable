# M11: In-App Settings — Design

## Summary

M11 adds a full settings screen so users can configure the sync target (server URL, username, app password, calendar) without hand-editing `~/.config/retaskable/config.toml`. It also serves as the first-run path: on a fresh device with no config file, opening Settings shows the empty form. When the user changes the sync target (server URL or calendar), the local task cache and pending-op queue are wiped so the next Sync starts clean. A credentials-only change (username or password without a server/calendar change) keeps the cache intact, preserving any queued offline ops.

Three new MSG pairs expose the settings flow:

| Request | Response | Purpose |
|---------|----------|---------|
| MSG 15 `get_config` | 115 | Reads current config; sends base_url, username, calendar, has_password bool |
| MSG 16 `save_config` | 116 | Writes config; resets cache if target changed |
| MSG 17 `discover_with` | 117 | Validates creds + lists calendars without saving |

## Key Decisions

### `config::load_optional()` for first-run safety

The existing `config::load()` writes a template and errors on a missing file. Settings needs to open even on first run, so `load_optional()` returns `Ok(None)` instead. `get_config` calls `load_optional()`; it returns `{"configured": false, "base_url": "", ...}` when no file exists so QML can show a blank form rather than an error.

### `get_config` never returns the password

`get_config` returns `has_password: bool` (`true` when `app_password` is non-empty). The actual password never round-trips to QML. `save_config`'s JSON payload carries the new password in the `app_password` field; a blank value means "keep existing". `config::merge_password(new_password, existing)` enforces this: blank new ⇒ keep existing string; non-blank ⇒ use new string. The QML `settingsPass` field uses `echoMode: TextInput.Password` and its placeholder reads `"•••• (unchanged — leave blank to keep)"` when `settingsHasPassword` is true.

### `target_changed` guards cache reset

`target_changed(old: Option<&Config>, base_url: &str, calendar: &Option<String>) -> bool` compares only the two fields that identify the data source. A return of `true` on `None` (no prior config) ensures first-run always starts with a clean cache. A return of `false` when only username/password changes preserves the queue so in-flight offline ops survive a password rotation.

`db::reset_cache` wipes `task`, `pending_op`, and `calendar` (which carries `sync_token` + `last_synced_at`) but leaves `meta` (schema version) intact. After a reset the next Sync's `get_sync_token` returns `None`, forcing a full sync-collection pull.

### MSG 17 `discover_with`: validate before saving

`discover_with_inner` constructs a temporary `config::NextcloudConfig` from the payload (blank password falls back to `load_optional`'s stored secret via `merge_password`) and calls `nextcloud::discover_calendars`. Nothing is written to disk. The response is `{"ok": true, "calendars": [...]}` or `{"ok": false, "error": "…"}`. QML's `applyDiscover` populates `calendarsModel` and reconciles `selectedCalendar`:
- If the previously-selected calendar name is absent from the discovered list, `selectedCalendar` is cleared (or auto-set if exactly one calendar was found).
- `needsDiscover` is set to `false` on success, unblocking the Save button.

The `needsDiscover` gate prevents saving a stale calendar name. Any change to the server URL or username fields fires `onTextChanged: root.needsDiscover = true`, which greys out and disables the Save button until "Test & Load Calendars" succeeds. This was the second hardware-surfaced bug: a user who had previously configured "Personal" as their calendar and then changed the server URL could hit Save and persist a calendar that didn't exist on the new server, causing every subsequent Sync to fail.

### Settings overlay + auto-discover on open

The settings UI is a `Rectangle` with `z: 100` that covers the main UI when `root.settingsOpen` is true. It is not a separate QML file or `StackView`; the overlay approach keeps the component tree flat (matching the project's no-component-separation style).

`openSettings()` fires `endpoint.sendMessage(15, "")` to populate the fields, then auto-calls `loadCalendars()` if URL and username are already filled in. This ensures the calendar picker is live on open, not stale. The `applyConfig` handler sets `root.needsDiscover = false` after populating the fields (the field assignments fire `onTextChanged` which sets it to `true` in sequence — the explicit clear after the loop overrides that).

After a successful Save, `applySaveResult` closes the overlay and immediately fires `endpoint.sendMessage(5, "")` to Sync. If the target changed, `reset_cache` wiped the local data, so the Sync does a full pull.

## Acceptance Criteria

1. Opening Settings on a fresh device (no `config.toml`) shows a blank form with no error.
2. `get_config` (MSG 15) returns `has_password: true` when a password is stored; never returns the password string itself.
3. `save_config` (MSG 16) with a blank `app_password` field preserves the existing stored password.
4. A change to `base_url` or `calendar` triggers `db::reset_cache`; a username-only change does not.
5. `discover_with` (MSG 17) lists calendars without writing anything to disk; blank password uses the stored credential.
6. The Save button is disabled (`needsDiscover = true`) after editing server URL or username; it re-enables only after a successful discover.
7. If the currently-selected calendar is absent from a fresh discovery, it is cleared (or auto-selected when exactly one calendar exists).
8. After Save, the overlay closes and a Sync fires automatically.
9. `config::merge_password`, `save_to`, and `load_optional` tests pass (6 new tests in `config.rs`); `reset_cache` and `target_changed` tests pass (4 new tests in `main.rs` and `db.rs`).

## Verification

Hardware-surfaced bugs fixed during this milestone:

- **Stale calendar on server change.** Entering a new `base_url` with the old calendar name pre-filled (`"Personal"`) and tapping Save without running "Test & Load Calendars" persisted an invalid config. Fixed by the `needsDiscover` gate.

- **Blank form on `applyConfig`'s `onTextChanged` storm.** Setting `settingsUrl.text` fired `onTextChanged → needsDiscover = true` before `applyConfig` could call `root.needsDiscover = false`. The explicit `root.needsDiscover = false` at the end of `applyConfig` (after all field assignments) is the fix.

- **`applyTaskList` left stale rows after a Settings-induced calendar switch.** Fixed in M10 (stale-list-on-non-JSON), but the same failure mode surfaced again after a target-changed Save: the immediate Sync after `reset_cache` returned `"calendar ... not yet synced"` before the new calendar was upserted. `applyTaskList`'s `taskModel.clear()` in the catch branch handles it.
